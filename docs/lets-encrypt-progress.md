| Finding 3 (post-implementation review, 2026-09-13): ACME account-key persistence | `Program.cs` used LettuceEncrypt-Archon's `PersistDataToDirectory(...)` for account-key durability across restarts, but decompiling `LettuceEncrypt.dll` (3.0.0, via `ilspycmd`) showed this single extension always registers a `FileSystemCertificateRepository` as an additional `ICertificateRepository`/`ICertificateSource` too — duplicating every issued certificate's full PFX (private key included) to disk outside the `Certificate` aggregate's lifecycle, uncleaned on deletion — with no separate `PersistAccountKeyToDirectory`-style extension in this library version. However, the library does expose a public `LettuceEncrypt.Accounts.IAccountStore` interface (`SaveAccountAsync`/`GetAccountAsync` over a plain `AccountModel`) as its own DI-registrable extension point, independent of certificate persistence. Implemented a small custom `AccountKeyFileStore : IAccountStore` (`src/ProxyManager/Acme/AccountKeyFileStore.cs`) that JSON-serializes only the `AccountModel` to a single file, registered directly in `Program.cs` in place of `PersistDataToDirectory` — account-key durability is preserved with no certificate/key duplication, since certificates already round-trip through `AggregateCertificateSource`/`AggregateCertificateRepository` against the `Certificate` aggregate. | `ilspycmd -t LettuceEncrypt.FileSystemStorageExtensions .../LettuceEncrypt.dll` decompile confirms `PersistDataToDirectory` unconditionally does `builder.Services.AddSingleton((ICertificateRepository)implementationInstance).AddSingleton((ICertificateSource)implementationInstance)`; `dotnet build ProxyManager.sln` succeeds with the replacement; 158/158 unit tests pass | Resolved — account-key-only path found and adopted, no accepted limitation needed |
